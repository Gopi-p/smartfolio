Case Study · LogDesk

Full request logging
without editing 100 APIs.

A large app with a big team and no logging, so nobody could tell who changed what. One middleware captured every write, and LogDesk made it readable. This is an internal tool, so I will keep the specifics light.

Why this happened

No logging, and no way to answer basic questions

One of the apps I worked on had no activity logging at all. When something went wrong, we could not tell who made a change, or when it happened. We were debugging blind.

The support cases were the worst part. Someone would say they clicked a button a few times and nothing updated. Or that something saved fine, but on reload the data was old again. Without logs, all we could do was guess.

So I decided to build a proper activity logging system. The hard part was never the logging itself. It was doing it without rewriting the whole codebase.

The constraints

Minimal changes, on a very big app

The app was large: a big team, many modules, and a lot of API endpoints. The obvious approach, adding logging to each endpoint by hand, would have meant huge changes everywhere and a lot of overhead. I wanted something that touched as little code as possible.

What I was working around

  • 01
    A big team all working in the same codebase at once.

  • 04

The insight

Two layers everything already went through

Instead of the endpoints, I looked at the layers around them. Every request came in through the routes, and every module did its database work through a shared service layer, the same set of helpers wrapped around the usual create, update and delete operations.

If I could watch those two layers, the way in and the database calls underneath, I could capture almost everything without touching the endpoints themselves.

Step 01

One middleware, on the write routes

The first piece is a single middleware, added only to the routes that change data (the POST, PUT, PATCH and DELETE calls). Reads are left alone. When a write comes in, it opens a small per-request context that carries who made the call, the time, the path, and the request body, with obvious secrets like passwords and tokens stripped out before anything is stored.

That context rides along with the request for its whole life using async local storage, so any code deeper in the stack can add to the same log entry without me passing anything around by hand.

Step 02

The service layer records itself

The second piece wraps the shared database service. Each write operation it runs quietly adds a step to the current request's log: which collection was touched, which operation, and how long it took. Because everything already went through this one layer, I got that for free across every module, without editing a single query.

When the same operation repeats in a loop, the steps collapse into one line with a count, so a request that updates fifty rows reads as one clear step instead of fifty noisy ones.

This is the part I am happiest with. The middleware knows the request, and the wrapped service knows the database work, so together they explain exactly what a request did, and neither one needed the endpoints to change.

Step 03

A non-blocking flush to OpenSearch

When the response goes out, the whole thing is assembled into one JSON log: who, when, the request, the response, the ordered steps, the total duration, and whether it succeeded or failed. That document is written to OpenSearch just after the response is sent, so logging never slows a request down. If a log fails to write, it is swallowed quietly, because logging should never be the reason a real request breaks.

The whole thing is reusable. Another team can drop in the same middleware, point it at their own index, and get end-to-end logging without building any of this. It is an import, not a project.

The viewer

LogDesk: the logs, made usable

Logs sitting in OpenSearch are only half the job. So I built LogDesk, a small internal web app to read them. You sign in, and it talks to the log store directly from the browser, with no backend of its own to maintain.

// Sign in and point it at a log index

The main view is a table of recent writes, newest first, with filters for time range, user, and API path, plus a search box. It is the view I wished I had during those support cases: who did what, and when.

// Filter by time, user or path, then scan the writes

Click any row and it opens up: the ordered steps the request ran, how long each took, and the original request and response bodies, pretty-printed. That is usually enough to settle a "did my change actually save" question in seconds instead of guesswork.
