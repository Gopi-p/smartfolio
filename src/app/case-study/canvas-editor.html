Why this happened

The layouts lived in CAD, and that hurt

The company kept every store's layout in CAD. Where the walls are, where the entrance is, how the fixtures are arranged, where each product sits. CAD is great for drafting. It is painful for everything else.

Updating a layout meant opening a CAD tool. Sharing one meant sending a file. Tracking what actually changed, or connecting a layout to live store data, was more or less impossible. And these layouts are not static. Product placements move around constantly, so the floor plan changes almost every day.

A format that needs a desktop tool and a trained hand does not fit a business that updates its stores that often. The layout needed to live somewhere the whole team could reach it.

The idea

Put it on the web, inside the app they already use

There was already a dashboard the team logged into every day. So instead of a separate tool, the layout editor would live right there. Open a store, see its floor plan, drag things around, save. No CAD, no file transfers, no training.

I built the canvas on Fabric.js. It gives you real objects to work with, selection, scaling, rotation, grouping, instead of raw canvas drawing calls. That is exactly what a layout editor needs, and it saved me from rebuilding all of that by hand.

The build

Walls, entrances and fixtures, all draggable

The canvas holds the pieces a store is actually made of. You drag them on, position them, resize and rotate, and build the layout up piece by piece. Everything stays editable in place, so it behaves like a design tool, not a form.

The data model

The canvas is just JSON underneath

The important call was treating the layout as data, not a picture. When you hit save, I pull each object's properties off the canvas, its x and y coordinates, dimensions, angle and colors, and store the whole layout as JSON in MongoDB.

Next time that store opens, I read the JSON back and re-render the exact same layout on the canvas. Nothing is flattened into an image, so every element stays live and editable, every single time.

Because the layout is structured data and not a drawing, it is not stuck inside the editor. Any other feature can read the same JSON and know exactly where every fixture sits.

Where it connects

One layout, feeding the whole product

The store layout is not a standalone drawing. It is connected to the rest of the web and mobile app, and the same layout drives features across the product. It also keeps changing, since product placements shift from one day to the next.

That connection is what made the layout worth building properly. Once the app knows where everything is, it can start putting real data on top of it.

The payoff

Real store data, on the actual floor plan

With the layout in place, we could map near real-time analytics onto the store itself. Footfall, pickup rate and customer counts, tied to the exact spots on the floor plan instead of sitting in a table somewhere.

  • Layouts editable on the web by anyone, with no CAD tool needed
  • Every store's plan saved as re-editable JSON, not a flat file
  • Daily product-placement changes captured without friction
  • Near real-time analytics (footfall, pickup rate, customer counts) mapped to the floor
  • One layout shared across the web and mobile app
