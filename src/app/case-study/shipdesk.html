Taking releases out of a chat thread,
into one calm flow.

Releases here move through a few manual steps and a few people, all coordinated in a chat channel. New to the team, I chose to tidy the flow rather than automate it. This is ShipDesk, an internal tool, so I will keep the specifics light.

Why this happened

The release lived in a chat channel

Almost every company has its own way of building and shipping, and this one is no exception. When I joined I noticed the release flow had a lot of small steps and pulled in a few people, even though the actual CI/CD was already automated.

Developers work on different modules, and each module is published as its own package. To get a release out, someone posts package names into a chat channel, a maintainer scans the thread and pulls them together, and eventually someone types "done" to close it out. Packages get missed. Late additions cause confusion. And there is no record of what actually went out.

How a release moved

A few hand-offs, all over chat

01

Dev publishes a package

A developer finishes a module, publishes the package, and posts the name and version into the channel.

02

Maintainer collects and tags

A maintainer reads through the thread, gathers the packages, updates the root project, and cuts a tag version.

03

Tag goes to DevOps

The tag is shared back in the channel, with DevOps mentioned.

04

DevOps runs the pipeline

DevOps kicks off the build against that tag, and the release ships.

The judgment call

Tidy the flow, do not automate it

I was completely new, so I did not fully understand why the flow was built this way. That mattered. Instead of assuming it was wrong and automating it away, I assumed it suited the team for reasons I had not learned yet.

So I did not touch the pipeline. I set out to close the communication gap and keep a record of every release, nothing more. A smaller, safer change that respects a process I did not build. I called it ShipDesk, and built it with AI-assisted development so it came together fast without pulling focus off my main work.

// ShipDesk, a small internal app to run releases
Step 01

A release with a deadline

A release starts with a project manager creating it and setting a submission deadline. Everything after that hangs off this one object, so there is always a single place to look instead of scrolling a chat.

When the deadline passes, submissions close on their own. There is no cron job behind it, the release just checks its own deadline the next time anyone opens it and closes itself if the time is up.

// A release is one object with a name and a deadline
Step 02

Developers add packages, behind a checklist

Before the deadline, each developer adds their packages to the release. Instead of a free-form chat message, it is a structured entry, so nothing is ambiguous later.

The part I like most is the checklist. Before a developer can finalise, they have to confirm a short list of release-hygiene questions. The checklist itself is editable, so the team can shape it around the mistakes they actually tend to make.

// Nothing gets finalised until the checklist is confirmed
Step 03

The release comes together in one view

Every submission rolls up onto the release page. The project manager can see what is in, close submissions early, or re-open a release with a new deadline if something was missed. The state everyone used to reconstruct from chat is now just the page.

// One page holds the whole release, no thread to piece together
Step 04

Maintainers hand off cleanly

When submissions close, the frontend and backend maintainers get their side laid out for them: the exact package block, the dependency lines ready to paste, and a formatted announcement to drop into the channel. They enter the tag version they cut and mark their side ready, and the build order stays sensible (backend first, then frontend).

The chat channel does not disappear, but the message posted into it is now generated, not typed by hand. That is the whole point: the same flow the team already trusted, with the error-prone copy-paste taken out of it.

// Copy the dependency block and the announcement, enter the tag, mark ready
  • Every release is one object with a deadline, not a scroll of messages
  • A mandatory checklist catches the usual misses before they ship
  • Dependency blocks and channel announcements are generated, not hand-typed
  • Backend-first build order is enforced instead of remembered
  • Every release is recorded, so there is finally a history to look back on
